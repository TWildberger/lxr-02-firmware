# LXR-02 SysEx protocol (v1)

This document specifies the System Exclusive protocol implemented by this
fork of the LXR-02 firmware (shown as **`1.7-sx`** on the boot screen). It lets
an editor/librarian read and write kits, patterns, global settings and single
parameters, and get notified when the user edits sounds on the device.

Stock Erica Synths firmware ignores all SysEx. Hosts must therefore probe with
`IDENTITY_REQUEST` first and fall back to plain CC/NRPN control
(see [`params.json`](params.json) `midi_rules`) when there is no answer.

Related documents:

* [`params.json`](params.json): machine-readable parameter table (ids, ranges,
  labels, CC/NRPN numbers). Generated by `tools/gen_params.py`.
* [`file-formats.md`](file-formats.md): SD card file layouts (`.snd`, `.pat`,
  `glo.cfg`, …). The SysEx kit and pattern payloads reuse these layouts.

## 1. Transport

* Works on **DIN MIDI** and **USB MIDI** (cable 0). Each reply goes to the
  port the request arrived on.
* Must be enabled on the device: **Global menu → page 3 → `SysEx` = on**
  (default on). With SysEx off, the firmware ignores all SysEx (including the
  universal identity request) and never transmits any.
* **Device ID** (`DeviceID`, 1–16, default 1) on the same page selects which
  requests the unit answers. `ParmEcho` (default off) enables
  [parameter notifications](#7-parameter-echo-device--host-notifications).
* The protocol is half duplex request/response. A host sends one request and
  waits for the reply (`ACK`, `NAK` or the requested data) before sending the
  next one. The only exception is `PARAM_SET`, which has no success reply and
  may be streamed. Use a reply timeout of **500 ms** (DIN) and allow
  **3 s** for a full pattern dump over DIN.
* The device processes the next request only once it has finished transmitting
  the previous reply. Requests keep queueing in a 512-byte receive buffer per
  port while it is busy; anything beyond that is lost, and the host then sees a
  timeout or a checksum `NAK`.
* Maximum accepted frame length (F0 … F7 inclusive) is **320 bytes**. It is
  also reported in the identity reply.

Rough throughput: DIN MIDI moves ≈3 kB/s, so a kit dump (≈300 bytes) takes
≈0.1 s and a pattern dump (≈4.3 kB) ≈1.4 s. USB is much faster.

## 2. Frame format

```
F0 7D 4C dd vv cc <payload…> ss F7
```

| Byte | Meaning |
|------|---------|
| `F0` | SysEx start |
| `7D` | Manufacturer ID: MIDI "non-commercial / educational use" |
| `4C` | Model byte (`'L'`, LXR-02) |
| `dd` | Device: `00`–`0F` = device ID 1–16, `7F` = all devices. Replies always carry the unit's own ID. |
| `vv` | Protocol version, `01` for this document |
| `cc` | Command, see [section 4](#4-command-summary) |
| payload | Command specific, every byte `00`–`7F` |
| `ss` | Checksum: XOR of all bytes from `dd` to the last payload byte, masked to 7 bits (`& 0x7F`) |
| `F7` | SysEx end |

Receive rules (device side; hosts should apply the same):

1. Frames whose header is not `F0 7D 4C` are ignored.
2. Frames addressed to another device ID (`dd` ≠ own ID and ≠ `7F`) are ignored.
3. On a bad checksum, the device answers `NAK(cc, ERR_CHECKSUM)`.
4. If `vv` ≠ `01`, the device answers `NAK(cc, ERR_VERSION)`. The one exception
   is `IDENTITY_REQUEST`, which is answered whatever `vv` is, so hosts can
   always discover the supported version.
5. Frames longer than 320 bytes are dropped and answered with
   `NAK(cc, ERR_LENGTH)` when the header could be read.
6. A frame interrupted by another status byte (other than real-time bytes
   `F8`–`FF`) is discarded.

> `7D` is the reserved non-commercial ID. It is not unique, so other DIY gear
> may use it too. The model byte, version byte and checksum keep accidental
> matches unlikely. A future official ID can be added without changing the
> rest of the frame.

## 3. Data encodings

* **u7**: one byte, 0–127.
* **u14**: two bytes, least significant 7 bits first:
  `value = b0 | (b1 << 7)`.
* **packed8**: arbitrary 8-bit data packed into 7-bit bytes. This is the same
  "7-in-8" scheme the original LXR front panel parser uses
  (`frontPanelParser.c`):
  * Raw data is split into groups of up to 7 bytes.
  * Each group is sent as the low 7 bits of every byte, followed by one
    *MSB byte* whose bit *i* holds bit 7 of raw byte *i* in that group.
  * A final short group of *k* bytes is sent as *k* bytes plus its MSB byte.
  * `N` raw bytes become `N + ceil(N / 7)` bytes.

  Example: raw `81 02 FF` → `01 02 7F 05`.
* **name**: 8 raw bytes (ASCII, padded with spaces or `00`), always sent as
  **packed8** (10 bytes on the wire).
* **parameter value**: always sent as **u14** in parameter messages. Most
  parameters are 0–127, but some (e.g. BPM, mod targets, mixer routing) go up to
  255. Kit/global dumps carry values as raw bytes inside packed8.

## 4. Command summary

| `cc` | Name | Direction | Reply |
|------|------|-----------|-------|
| `01` | `IDENTITY_REQUEST` | host → device | `IDENTITY_REPLY` |
| `02` | `IDENTITY_REPLY` | device → host | — |
| `03` | `STATUS_REQUEST` | host → device | `STATUS_REPLY` |
| `04` | `STATUS_REPLY` | device → host | — |
| `10` | `KIT_REQUEST` | host → device | `KIT_DUMP` |
| `11` | `KIT_DUMP` | both | to device: `ACK` |
| `12` | `KIT_STORE` | host → device | `ACK` |
| `13` | `KIT_LOAD` | host → device | `ACK` |
| `14` | `KIT_NAME` | host → device | `ACK` |
| `20` | `PATTERN_REQUEST` | host → device | `PATTERN_CHUNK` × n |
| `21` | `PATTERN_CHUNK` | both | to device: `ACK` per chunk |
| `22` | `PATTERN_NAME` | host → device | `ACK` |
| `30` | `GLOBALS_REQUEST` | host → device | `GLOBALS_DUMP` |
| `31` | `GLOBALS_DUMP` | both | to device: `ACK` |
| `40` | `PARAM_GET` | host → device | `PARAM_VALUE` |
| `41` | `PARAM_SET` | host → device | none (only `NAK` on error) |
| `42` | `PARAM_VALUE` | device → host | — |
| `43` | `PARAM_NOTIFY` | device → host | — |
| `44` | `ECHO_SET` | host → device | `ACK` |
| `45` | `EVENT` | device → host | — |
| `7E` | `ACK` | device → host | — |
| `7F` | `NAK` | device → host | — |

Unknown commands are answered with `NAK(cc, ERR_UNKNOWN_CMD)`.

### Slot numbers

* Kits: `00`–`3F` = the 64 kit slots held in RAM (the slots you see on the
  kit load/save pages). `7F` = **edit buffer**, the sound currently playing.
* Patterns: `00`–`3F` = the 64 pattern slots in RAM. `7F` = the **active
  (playing) pattern**.

Kit and pattern slots live in RAM and are only written to the SD card when
the request sets the `SAVE` flag, or when the user saves on the device.

### Flags byte (`ff`)

Used by commands that write data:

| Bit | Name | Meaning |
|-----|------|---------|
| 0 | `SAVE` | Also write the result to the SD card (same file the device's own *save* function writes) |
| 1–6 | — | Reserved, send 0 |

## 5. Message reference

### 5.1 `IDENTITY_REQUEST` (`01`)

No payload. Send it with `dd = 7F` to find a unit whatever its device ID.

Example (complete frame): `F0 7D 4C 7F 01 01 7F F7`

### 5.2 `IDENTITY_REPLY` (`02`)

| Field | Encoding | Value in this firmware |
|-------|----------|------------------------|
| protocol version | u7 | 1 |
| firmware major, minor, patch | 3 × u7 | 1, 7, 0 |
| firmware version string | 8 × u7 ASCII, `00`-padded | `"1.7-sx"` |
| `NUM_PARAMS` | u14 | 305 |
| `END_OF_SOUND_PARAMETERS` (kit length) | u14 | 247 |
| `PAR_BEGINNING_OF_GLOBALS` | u14 | 272 |
| kit slots | u7 | 64 |
| pattern slots | u7 | 64 |
| tracks | u7 | 7 |
| steps per track | u7 | 64 |
| pattern data length (raw bytes) | u14 | 3657 |
| max accepted frame length | u14 | 320 |
| capability bits | u14 | see below |
| device ID − 1 | u7 | 0–15 |
| parameter echo on | u7 | 0/1 |

Capability bits:

| Bit | Feature |
|-----|---------|
| 0 | Kits (`10`–`14`) |
| 1 | Patterns (`20`–`22`) |
| 2 | Globals (`30`–`31`) |
| 3 | Single parameters (`40`–`42`) |
| 4 | Echo/notifications (`43`–`45`) |
| 5 | `SAVE` flag (SD card writes) |

Hosts must size their buffers from these numbers rather than hard-coding them.
`NUM_PARAMS`, `END_OF_SOUND_PARAMETERS` and `PAR_BEGINNING_OF_GLOBALS` must
match the `counts` block of the `params.json` the host was built with. If they
differ, the host should only use parameter ids both sides know.

### 5.3 Universal identity request

When SysEx is enabled, the unit also answers the standard MIDI universal
identity request `F0 7E <id> 06 01 F7`, where `<id>` is `7F` or its device
ID − 1:

```
F0 7E <id> 06 02 7D 4C 00 01 00 <major> <minor> <patch> <protocol> F7
```

(manufacturer `7D`, family `4C 00`, member `01 00`, version `01 07 00 01`).

### 5.4 `STATUS_REQUEST` (`03`) / `STATUS_REPLY` (`04`)

Request has no payload. Reply:

| Field | Encoding |
|-------|----------|
| current kit slot (last kit loaded or saved) | u7 |
| active pattern | u7 |
| sequencer running | u7 (0/1) |
| parameter echo on | u7 (0/1) |

### 5.5 `KIT_REQUEST` (`10`)

| Field | Encoding |
|-------|----------|
| slot | u7 (`00`–`3F`, `7F` = edit buffer) |

Example, request the edit buffer: `F0 7D 4C 7F 01 10 7F 11 F7`

### 5.6 `KIT_DUMP` (`11`)

| Field | Encoding |
|-------|----------|
| slot | u7 |
| flags | u7 (device → host: always 0) |
| parameter count *n* | u14 (device → host: 247) |
| data | packed8 of `name[8]` followed by *n* parameter bytes |

The data is the same layout as an `.snd` file: name, then sound parameters
0 … *n*−1. See `scope == "sound"` entries in `params.json`. For the edit
buffer (`7F`) the device reports the name of the current kit slot.

Host → device:

* **`slot = 7F`**: the parameters replace the edit buffer and are applied to
  the sound engine immediately, like loading a kit. The name is ignored and the
  current kit slot number does not change. `SAVE` is not allowed here
  (`NAK ERR_RANGE`); use `KIT_STORE` instead.
* **`slot = 00`–`3F`**: name and parameters are written to that RAM slot. The
  edit buffer is **not** changed, even if it is the current kit; send
  `KIT_LOAD` afterwards to hear it. With `SAVE`, the slot is also written to
  the SD card as `.snd`.
* If *n* is less than 247, parameters ≥ *n* keep their old value. If *n* is
  greater than 247, the extra values are ignored.
* Every value is clamped to the parameter's legal range (same limits as the
  front panel). Modulation-target indices beyond the target table become 0.
* Reply: `ACK(11, slot)`, or `NAK` (`ERR_LENGTH` if the data is shorter than
  `8 + n` bytes, `ERR_RANGE` for a bad slot, `ERR_SD` if saving failed).

### 5.7 `KIT_STORE` (`12`)

| Field | Encoding |
|-------|----------|
| slot | u7 (`00`–`3F`) |
| flags | u7 |

Copies the edit buffer into the slot and makes it the current kit. This is the
same as *save kit* on the device. With `SAVE`, the `.snd` file is written too.
Reply `ACK(12, slot)`.

### 5.8 `KIT_LOAD` (`13`)

| Field | Encoding |
|-------|----------|
| slot | u7 (`00`–`3F`) |

Loads the slot into the edit buffer and makes it the current kit. This is the
same as *load kit* on the device, including storing the kit number in the
active pattern. Reply `ACK(13, slot)`.

### 5.9 `KIT_NAME` (`14`) / `PATTERN_NAME` (`22`)

| Field | Encoding |
|-------|----------|
| slot | u7 (`00`–`3F`; `7F` = current kit / active pattern) |
| name | packed8, 8 bytes |

Renames a slot in RAM. Send the matching store/save request (or set `SAVE` on
a dump) to persist it. Reply `ACK(cc, slot)`.

### 5.10 `PATTERN_REQUEST` (`20`)

| Field | Encoding |
|-------|----------|
| slot | u7 (`00`–`3F`, `7F` = active pattern) |

The device answers with all chunks of the pattern, back to back. The host does
not acknowledge them.

### 5.11 `PATTERN_CHUNK` (`21`)

| Field | Encoding |
|-------|----------|
| slot | u7 |
| flags | u7 (device → host: 0; host → device: only read from chunk 0) |
| chunk index *i* | u7 |
| chunk count *c* | u7 |
| total raw length *L* | u14 (3657 in this firmware) |
| data | packed8 of this chunk's raw bytes |

The raw pattern data is `name[8]` followed by the 3649-byte pattern body
described in [file-formats.md](file-formats.md#pattern-body). It is the `.pat`
file minus the `PatV03` tag.

* Chunks carry at most **196 raw bytes** (224 bytes packed). The device sends
  `c = 19` chunks: 18 × 196 bytes plus a final 129 bytes. Hosts may use any
  chunk size from 1 to 196 raw bytes, as long as chunks are sent in order.
* Host → device: chunk 0 starts a new transfer and discards any unfinished
  one. Every chunk must have `i` = previous + 1 and the same slot, *c* and *L*;
  otherwise the device answers `NAK(21, ERR_SEQUENCE, i)` and discards the
  transfer. Each chunk is acknowledged with `ACK(21, i)`. Wait for it before
  sending the next chunk.
* After the last chunk (`i = c − 1`), the device checks that exactly *L*
  bytes arrived and that *L* equals its own pattern length (`ERR_LENGTH`
  otherwise). It then writes the slot, and the `ACK` of the last chunk is only
  sent after this commit.
  * If the slot is the active pattern, the change is made permanent: the
    device's undo/backup copy is updated too, so switching patterns does not
    revert it.
  * With `SAVE` (from chunk 0), the `.pat` file is written as well.
* Pattern contents are trusted the same way `.pat` files are: they are not
  range-checked beyond length. Only send data obtained from a dump or built
  according to the documented layout.
* Writing the pattern that is currently playing is allowed; the switch-over
  is atomic.

### 5.12 `GLOBALS_REQUEST` (`30`) / `GLOBALS_DUMP` (`31`)

Request has no payload. Dump:

| Field | Encoding |
|-------|----------|
| flags | u7 (device → host: 0) |
| first parameter id | u14 (= `PAR_BEGINNING_OF_GLOBALS`, 272) |
| count *n* | u14 (33 in this firmware) |
| data | packed8 of *n* value bytes (ids `first` … `first + n − 1`) |

This is the same order as `glo.cfg`. Host → device:

* `first` must equal the device's `PAR_BEGINNING_OF_GLOBALS`, otherwise
  `NAK ERR_RANGE`.
* Each value is clamped and applied as if changed in the global menu.
* `SysEx` enable (302) and `DeviceID` (303) are **read-only over SysEx** and
  skipped, so a host cannot lock itself out.
* With `SAVE`, `glo.cfg` is written.
* Reply `ACK(31, n)`.

### 5.13 `PARAM_GET` (`40`) / `PARAM_VALUE` (`42`)

`PARAM_GET` payload: 1–64 × u14 parameter id.
`PARAM_VALUE` payload: the same number of `(u14 id, u14 value)` pairs, in
request order.

Any id ≥ `NUM_PARAMS` → `NAK(40, ERR_RANGE, id)`.

### 5.14 `PARAM_SET` (`41`)

Payload: 1–64 × `(u14 id, u14 value)`.

* Applied in order to the edit buffer (sound ids) or the global settings
  (global ids). Values are clamped exactly like front-panel edits, and the
  sound engine and display are updated.
* There is **no reply on success**, so knob movements can be streamed. On the
  first invalid pair the device stops and answers `NAK(41, err, id)`. Pairs
  before it stay applied.
  * `ERR_RANGE`: id ≥ `NUM_PARAMS`.
  * `ERR_READ_ONLY`: ids `END_OF_SOUND_PARAMETERS` … `PAR_BEGINNING_OF_GLOBALS − 1`
    (`scope == "pattern"`, step/track UI context), and `SysEx`/`DeviceID`.
* Global changes are not saved to `glo.cfg` automatically. Use `GLOBALS_DUMP`
  with `SAVE`, or the device's *save globals*.
* Changes made with `PARAM_SET` are not echoed back as `PARAM_NOTIFY`.

Example: set parameter 3 to 100:
`F0 7D 4C 7F 01 41 03 00 64 00 58 F7`

### 5.15 `ECHO_SET` (`44`)

Payload: u7 `0` = off, `1` = on. Sets `ParmEcho` for the running session (not
saved to `glo.cfg`). Reply `ACK(44, state)`. A typical editor sends
`ECHO_SET 1` after a successful identity request and `ECHO_SET 0` on
disconnect.

### 5.16 `PARAM_NOTIFY` (`43`) / `EVENT` (`45`)

See [section 7](#7-parameter-echo-device--host-notifications).
`PARAM_NOTIFY` uses the same pair format as `PARAM_VALUE`, with up to 32 pairs.

`EVENT` payload:

| Field | Encoding |
|-------|----------|
| event type | u7 |
| argument | u14 |

| Type | Name | Argument | Host action |
|------|------|----------|-------------|
| `01` | `KIT_CHANGED` | current kit slot | Edit buffer changed wholesale (kit load, project load, …). Re-request kit `7F` and globals. |
| `02` | `PATTERN_CHANGED` | active pattern | Active pattern switched |

### 5.17 `ACK` (`7E`) / `NAK` (`7F`)

| Field | `ACK` | `NAK` |
|-------|-------|-------|
| command being answered | u7 | u7 |
| error code | — | u7 |
| argument (slot, chunk index, id, …) | u14 | u14 |

Error codes:

| Code | Name | Meaning |
|------|------|---------|
| `01` | `ERR_CHECKSUM` | Checksum mismatch |
| `02` | `ERR_UNKNOWN_CMD` | Command not supported |
| `03` | `ERR_LENGTH` | Payload too short/long, frame too long, or wrong total length |
| `04` | `ERR_RANGE` | Slot, id or field out of range |
| `05` | `ERR_BUSY` | Reserved |
| `06` | `ERR_SEQUENCE` | Pattern chunk out of order or inconsistent |
| `07` | `ERR_VERSION` | Unsupported protocol version |
| `08` | `ERR_READ_ONLY` | Parameter cannot be written over SysEx |
| `09` | `ERR_SD` | SD card write failed (argument = FatFs result code) |

## 6. Parameter ids

Parameter ids are the firmware's `PAR_*` enum values (0 … `NUM_PARAMS` − 1).
They are listed with ranges, labels and scopes in `params.json`:

| Range | Scope | Notes |
|-------|-------|-------|
| 0 – 246 | `sound` | Kit parameters, stored in `.snd`/kit dumps |
| 247 – 271 | `pattern` | Step-edit/track UI context, read-only over SysEx |
| 272 – 304 | `global` | Stored in `glo.cfg`, `GLOBALS_DUMP` order |

Modulation destinations (`PAR_VEL_DEST_*`, `PAR_TARGET_LFO*`,
`PAR_P1_DEST`/`PAR_P2_DEST`) hold an **index into `mod_targets`** in
`params.json`, not a parameter id.

## 7. Parameter echo (device → host notifications)

With `ParmEcho` on (global menu or `ECHO_SET 1`):

* About every 20 ms, the device sends every parameter the user changed **on
  the device** since the last scan (knobs, encoder, menus, buttons) as
  `PARAM_NOTIFY` frames of up to 32 pairs. Several changes to the same
  parameter within one interval are merged into the latest value.
* Changes caused by incoming MIDI (CC/NRPN from any source) or SysEx
  (`PARAM_SET`, `KIT_DUMP`, …) are **not** echoed, so an editor does not get its
  own edits back.
* If more than 24 parameters change in one interval (kit or project load,
  etc.), the device sends a single `EVENT KIT_CHANGED` instead. The host
  should then re-request kit `7F` (and globals).
* A change of the active pattern sends `EVENT PATTERN_CHANGED`.
* Notifications go to the port of the most recent valid SysEx request, or to
  both ports if there has been none since power-up. They are held back while
  a reply is being sent.
* Not reported in v1: step/pattern edits, mutes, transport state. Re-request
  the pattern or `STATUS` if you need them.

## 8. Typical host sequences

**Connect**

1. `IDENTITY_REQUEST` (`dd = 7F`). No reply within 500 ms → stock firmware,
   use CC/NRPN only.
2. Check the counts against `params.json`, remember the device ID.
3. `ECHO_SET 1`, `KIT_REQUEST 7F`, `GLOBALS_REQUEST`, `STATUS_REQUEST`.

**Edit a sound**: `PARAM_SET` (streamed), or CC/NRPN.

**Librarian upload of a kit to slot 12 and save it**:
`KIT_DUMP slot=0C flags=SAVE …` → `ACK`.

**Backup all patterns**: `PATTERN_REQUEST 00` … `3F`, one at a time.

## 9. Versioning

* New commands and new trailing fields may be added without changing `vv`.
  Hosts must ignore unknown commands, unknown event types and extra trailing
  payload bytes.
* Incompatible changes increase `vv`.
* Parameter ids follow the firmware's `Parameters.h`. If a later firmware
  inserts parameters, the counts in the identity reply change and hosts must
  use a matching `params.json`.
